//Deployment architecture: each building has a Raspberry Pi 5 acting as edge gateway. IoT devices (smart meters, environmental sensors, smart plugs) publish data locally via MQTT broker running on the Pi. All processing and data storage happen locally by default — building data stays within the building unless the user explicitly authorizes sharing.

//Inter-building communication uses Tailscale VPN overlay network. Buildings that opt-in to community sharing expose selected data topics to other buildings or to the community aggregator/DSO. Tailscale provides encrypted peer-to-peer connections without exposing nodes to the public internet.

//Community-level services (aggregation, flexibility coordination, community dashboards) run on a central node or cloud instance accessible through the same Tailscale network. These services only consume data that buildings have explicitly made available.

### 1.1.1    Contribution to Comprehension

//Comprehension — tools that help users and operators understand what is happening in the building and community

//XAI provides interpretable explanations of energy consumption patterns, comfort preferences, and flexibility potential. Users can understand why certain recommendations or actions are made.

//Federated learning models trained across buildings without sharing raw data — each building contributes to community-level models while preserving privacy. Comprehension of community-wide patterns emerges without centralizing sensitive data.

//Dashboards and visualizations present building-level and community-level energy data, comfort metrics, and flexibility status in an accessible way.

### 1.1.2    Contribution to Decision

//Decision — digital twins and dashboards that support informed decision making

//Digital twin of each building represents current state: energy consumption, production (if prosumer), occupancy, comfort levels, device status. Updated in real-time from IoT data via MQTT.

//Community-level digital twin aggregates opted-in building data to provide DSO and aggregator with overview of available flexibility, consumption forecasts, and community energy balance.

//Dashboards present decision-relevant information: energy prices, flexibility requests from upstream operator, comfort trade-offs, cost optimization opportunities.

### 1.1.3    Contribution to Action

//Action — detection and response mechanisms that execute decisions

//Flexibility activation: when upstream operator requests flexibility or when energy prices make it advantageous, local agents on each Pi can activate pre-agreed flexibility measures (shift loads, adjust setpoints) with user consent.

//Anomaly detection on local energy and comfort data — alerts when consumption deviates from expected patterns or when device malfunctions are detected.

//Automated responses within user-defined boundaries: comfort preferences set limits on what the system can adjust autonomously. Actions beyond those limits require explicit user approval.

//Community-level coordination: aggregator collects flexibility offers from buildings and responds to DSO requests, distributing actions across willing participants.

### 1.1.4    Summary

//UC4 provides situational awareness for energy communities through a privacy-preserving distributed architecture. Each building operates independently at the edge, sharing data only when authorized. Comprehension is achieved through XAI and federated learning, decisions are supported by digital twins and dashboards, and actions are executed through flexible, user-consented automation. Together, these layers enable optimized energy use, comfort-aware flexibility, and reliable community coordination.
