## Overview

This document defines the scientific use cases for the **Human-Centric Agent-based Adaptive Intelligent Communities (HAAIC) Framework**. The use cases are structured to progressively increase in scope: the first three isolate distinct architectural subsystems to allow independent validation, while the fourth presents a complete end-to-end scenario that integrates all components.

Each use case is specified with actors, preconditions, interaction flows, exercised system components, and the KPIs and research questions it validates.

---

## UC1 – Implicit Preference Learning from Sensor Streams

### 1.1 Goal

Validate that the HGNN-based preference model can correctly infer an occupant's comfort preferences from implicit sensor observations, without requiring explicit user input, and use them to autonomously adjust building actuators within a single zone.

This use case isolates the **Data Ingestion & Digital Twin (WP3)** and **User Preference Modeling (WP4)** subsystems.

### 1.2 Actors

| Actor | Role |
|---|---|
| Occupant A | Single user occupying the zone |
| Building Agent (Zone A) | Autonomous agent managing zone A |
| Digital Twin | Real-time model of the physical zone |
| HGNN Preference Model | Infers latent user preferences from context |
| Kafka Pipeline | Ingests sensor events from zone A |

### 1.3 Preconditions

- Zone A is instrumented with temperature, CO₂, occupancy, and lighting sensors.
- Occupant A has previously interacted with the zone for at least one work session (cold-start assumption: at least minimal history exists).
- The HGNN graph schema is initialized with user, context, and environment node types.
- The building agent has a configured autonomy envelope (e.g., temperature: 20–24 °C, lighting: 300–800 lux).

### 1.4 Main Flow

1. **Sensor ingestion:** Temperature and CO₂ sensors emit events every 30 seconds. The Kafka pipeline ingests and routes these to the Digital Twin topic for zone A. *(FR1.1, FR1.3)*
2. **Digital Twin update:** The DT state for zone A is updated within the configured latency threshold (≤500 ms). The DT stores timestamped state for all entities in zone A. *(FR2.1, FR2.4)*
3. **Preference inference trigger:** The building agent queries the HGNN model with the current graph state (user A node, contextual nodes: time-of-day = "morning", occupancy = 1, season = "winter"). *(FR3.1, FR3.3)*
4. **HGNN inference:** The model returns a ranked preference vector for temperature and lighting, each annotated with a confidence score. Example output: `{temperature: 22.5 °C, confidence: 0.87; lighting: 500 lux, confidence: 0.72}`. *(FR3.2, FR3.5)*
5. **Decision and actuation:** The inferred setpoints are within the agent's autonomy envelope. The agent issues actuation commands to the HVAC and lighting actuators. The decision is logged with the input context and confidence values. *(FR6.1, FR6.2, FR6.3, NFR7.1)*
6. **Model update:** Occupant A does not override the actuation (implicit acceptance). The acceptance event is recorded as a positive feedback signal. The HGNN model is updated incrementally without full retraining. *(FR3.4)*
7. **Preference drift scenario (variant):** After 4 weeks, Occupant A's preferred temperature shifts to 21 °C (e.g., seasonal change). The HGNN detects drift within N ≤ 10 interactions and updates the preference vector accordingly. *(M-WP4-03)*

### 1.5 Alternative Flow – Preference Override

At step 5, if Occupant A manually overrides the setpoint via the dashboard (raises temperature to 23 °C), the agent records this as an explicit negative correction. The HGNN model treats the override as a high-weight feedback signal and updates preference embeddings accordingly.

### 1.6 Components Exercised

| Component | FR/NFR |
|---|---|
| Kafka ingestion pipeline | FR1.1–FR1.4 |
| Digital Twin state update | FR2.1, FR2.4, NFR4.2 |
| HGNN preference model (inference) | FR3.1–FR3.5 |
| Incremental model update | FR3.4 |
| Agent decision cycle | FR6.1–FR6.3 |
| DP-SGD training mechanism | FR3.7, FR3.8 (training phase) |

### 1.7 KPIs Validated

| KPI | Target |
|---|---|
| M-WP4-01 – Preference Prediction Accuracy (HR@5) | ≥ 80% |
| M-WP4-03 – Preference Drift Adaptation Speed | N ≤ 10 interactions |
| M-WP4-06 – HGNN vs. Baseline Improvement | Δ ≥ 15% over best baseline |
| M-WP3-01 – Ingestion Latency | P95 ≤ 500 ms |
| M-WP5-06 – Decision Cycle Latency | P95 ≤ 2000 ms |

### 1.8 Research Questions Addressed

- **RQ1:** Can heterogeneous GNNs accurately model user comfort preferences from implicit sensor data in a single-occupant setting?
- **RQ0:** Does the data ingestion and Digital Twin infrastructure meet real-time performance requirements?

## UC2 – Multi-Occupant Conflict Resolution via LLM-Mediated Dialogue

### 2.1 Goal

Validate that the system can detect preference conflicts between two or more occupants sharing a zone, attempt autonomous resolution via a Pareto-optimal compromise strategy, and — when the resolution falls outside the agent's autonomy envelope — escalate to the affected users via a grounded LLM dialogue, achieving an acceptable outcome from both users' perspectives.

This use case isolates the **Conflict Detection (WP4)** and **LLM/SLM Interaction Layer (WP4/WP5)** subsystems.

### 2.2 Actors

| Actor | Role |
|---|---|
| Occupant A | Prefers cooler temperatures (preference: 20 °C) |
| Occupant B | Prefers warmer temperatures (preference: 24 °C) |
| Building Agent (Zone A) | Detects conflict and drives resolution |
| HGNN Conflict Model | Identifies conflicting preference vectors |
| SLM Dialogue Module | Mediates via natural language with both users |
| Digital Twin | Provides current zone state as MCP context |

### 2.3 Preconditions

- Both occupants have established preference models in the HGNN (UC1 has been executed for both).
- The zone currently sets temperature at 22 °C (neutral setpoint).
- The SLM is deployed locally on the edge device (meeting NFR5.1).
- The MCP JSON schema is pre-configured to include zone state, active preference profiles, and conflict summary.

### 2.4 Main Flow

1. **Simultaneous occupancy detection:** Occupancy sensors register both Occupant A and Occupant B in zone A. The Digital Twin is updated to reflect dual occupancy. *(FR2.1)*
2. **Preference retrieval:** The building agent queries the HGNN for both users' current preference profiles under the current context (dual occupancy, midday, spring). *(FR3.6)*
3. **Conflict detection:** The conflict identification model evaluates the preference vectors: `{A: 20 °C} vs. {B: 24 °C}`. The divergence exceeds the conflict threshold (Δ > 2 °C). A conflict event is logged. *(FR4.1, FR4.4)*
4. **Autonomous compromise attempt:** The agent applies the compromise resolution strategy: `T_compromise = weighted_mean(T_A, T_B, w_A, w_B)`. With equal weights: `T_compromise = 22 °C`. The agent evaluates whether this compromise is within autonomy bounds. 22 °C is within the envelope → agent actuates and notifies both users via the dashboard. *(FR4.2, FR6.3)*
5. **Escalation variant (conflict too sharp):** If Occupant A's preference is 19 °C and Occupant B's is 25 °C, the compromise (22 °C) deviates by 3 °C from each user's ideal — exceeding the agent's confidence threshold for autonomous resolution. The agent escalates. *(FR4.3, FR6.3)*
6. **MCP context construction:** The agent assembles the MCP payload: current zone temperature (21 °C), active user preferences, conflict summary, and proposed compromise (22 °C). *(FR5.2)*
7. **SLM dialogue — Occupant A:** The SLM initiates: *"Zone A currently has two occupants. I've proposed 22 °C as a compromise. You prefer 19 °C. Is this acceptable, or would you like to suggest an alternative?"* Occupant A responds: *"I can accept 21 °C at most."* The SLM extracts the preference signal and persists it to the HGNN. *(FR5.1, FR5.4, FR5.6)*
8. **SLM dialogue — Occupant B:** Similar exchange. Occupant B accepts 21 °C.
9. **Resolution commit:** The agent updates the setpoint to 21 °C and logs the resolution outcome and both users' acceptance. *(FR4.4)*
10. **Unresolved escalation (variant):** If no agreement is reached after the dialogue (e.g., B insists on ≥ 23 °C), the agent escalates to a human administrator and maintains the last safe setpoint. *(FR4.3)*

### 2.5 Components Exercised

| Component | FR/NFR |
|---|---|
| HGNN conflict detection model | FR4.1, FR4.4 |
| Compromise resolution strategy | FR4.2 |
| MCP JSON context construction | FR5.2 |
| SLM dialogue module | FR5.1, FR5.3–FR5.6 |
| Preference signal extraction from NL | FR5.4 |
| Bounded autonomy escalation logic | FR6.3 |
| NFR – LLM grounding (no hallucination) | FR5.6, NFR7.1 |

### 2.6 KPIs Validated

| KPI | Target |
|---|---|
| M-WP4-04 – Conflict Resolution Accuracy (Pareto-optimality) | ≥ 70% |
| M-WP5-01 – Task Completion Rate (dialogue → preference commit) | ≥ 85% |
| M-WP5-02 – Dialogue Efficiency (turns-to-consensus) | T̄ ≤ 4 turns |
| M-WP5-03 – Hallucination Rate | ≤ 5% |
| M-WP5-05 – Proactive Escalation Precision | ≥ 80% |
| M-USR-02 – Conflict Resolution Success Rate (user acceptance) | ≥ 65% |

### 2.7 Research Questions Addressed

- **RQ1:** Does the HGNN-based conflict model produce Pareto-optimal compromises for multi-occupant scenarios?
- **RQ2:** Can an MCP-grounded SLM dialogue effectively elicit and commit preference updates in a conflict mediation context?

## UC3 – Privacy-Preserving Cross-Building Preference Aggregation with P2P Resource Sharing

### 3.1 Goal

Validate that two building agents in adjacent units can share aggregated preference insights and computational resources via the P2P protocol, while enforcing Local Differential Privacy (LDP) at the data source and Differential Privacy (DP) on shared model outputs — without exposing individual user data to peer agents, and without requiring a central coordinator.

This use case isolates the **Privacy Mechanisms (WP4)** and **P2P Resource Sharing (WP5)** subsystems, with a focus on **RQ4**.

### 3.2 Actors

| Actor | Role |
|---|---|
| Building Agent A (Unit A) | Initiates resource-sharing request |
| Building Agent B (Unit B) | Responds with shared resource offer |
| DP Accountant Module | Tracks per-user ε budget consumption |
| LDP Perturbation Layer | Applies local noise before data leaves edge |
| P2P Protocol Layer | Mediates inter-agent resource negotiation |
| Occupants A₁, A₂, B₁ | Residents of respective building units |

### 3.3 Preconditions

- Unit A's HGNN has been trained on its own occupants' data (A₁, A₂) using DP-SGD (ε_A = 3.0).
- Unit B's HGNN is available for federated-style collaboration.
- Both agents are registered in the P2P peer discovery layer.
- Per-user privacy budget: ε_max = 10.0, with tracking via Rényi DP composition.
- LDP perturbation is configured for temperature preferences: Laplace mechanism with sensitivity Δf = 1.0 °C, ε_LDP = 2.0.

### 3.4 Main Flow

1. **Capability gap detection:** Agent A determines that its HGNN performance for new occupant A₂ is insufficient (HR@5 < 70%, below threshold) due to limited interaction history. It queries the P2P service registry for peer agents with compatible graph schemas. *(FR7.1, FR8.1)*
2. **Peer discovery and negotiation:** Agent A broadcasts a resource request: *"Seeking aggregated temperature preference embeddings for winter/morning context."* Agent B responds with an offer: *"Available: aggregated embeddings for 1 occupant, LDP-perturbed, ε_LDP = 2.0."* The P2P negotiation protocol resolves the exchange terms. *(FR8.1, FR8.2, FR6.4, FR6.5)*
3. **LDP perturbation at source:** Before Agent B transmits occupant B₁'s preference signal, the LDP layer applies the Laplace mechanism to the raw temperature preference value (B₁: 23 °C → noisy output: 22.3 °C ± ε_LDP). Only the perturbed value is transmitted. *(FR8.5, NFR3.8)*
4. **Data minimization enforcement:** The P2P protocol validates the outgoing payload against the minimal MCP schema: only `{context_type, perturbed_preference, noise_params}` fields are included. No user ID, occupancy schedule, or raw sensor history is transmitted. *(FR8.4, M-PRI-04)*
5. **Privacy budget accounting:** The DP accountant on Unit B logs the ε expenditure for this query against occupant B₁'s budget. `ε_remaining = ε_max − ε_cumulative`. If the budget is exhausted, the query is blocked. *(NFR3.6, NFR3.7, M-PRI-01)*
6. **HGNN warm-start on Unit A:** Agent A incorporates the received (perturbed) embedding as a soft prior in occupant A₂'s graph, improving initial inference accuracy without ever accessing raw B₁ data. *(FR3.2, FR3.4)*
7. **Post-sharing validation:** Agent A evaluates HR@5 for A₂ on the next 5 interactions. The metric is expected to recover to ≥ 75%, demonstrating utility of the privacy-preserving transfer. *(M-PRI-03, M-WP4-01)*
8. **Central coordinator failure (resilience variant):** The P2P service registry is made unavailable (network partition). Agents A and B complete the exchange using direct P2P addressing without degradation. *(FR8.2, M-SCL-03)*

### 3.5 Components Exercised

| Component | FR/NFR |
|---|---|
| P2P peer discovery and negotiation | FR6.4, FR6.5, FR8.1, FR8.2 |
| LDP perturbation layer (Laplace mechanism) | FR8.5, NFR3.8 |
| Data minimization schema enforcement | FR8.4 |
| DP budget accountant (Rényi composition) | NFR3.6, NFR3.7 |
| DP-SGD training mechanism (Unit A retraining) | FR3.7, FR3.8 |
| HGNN incremental update with external prior | FR3.4 |
| Resource revocation (optional) | FR8.3 |

### 3.6 KPIs Validated

| KPI | Target |
|---|---|
| M-PRI-01 – DP Budget Compliance Rate | 100% |
| M-PRI-02 – Empirical Privacy Leakage (MIA) | MIA_acc ≤ 55% |
| M-PRI-03 – LDP Utility-Privacy Trade-off | ΔAcc_LDP ≤ 10 pp |
| M-PRI-04 – Data Minimization Compliance in P2P | 100% |
| M-WP5-10 – Multi-agent Negotiation Success Rate | ≥ 90% |
| M-SCL-03 – P2P Resource Availability (offline) | ≥ 70% |

### 3.7 Research Questions Addressed

- **RQ4:** Can the HAAIC framework enforce meaningful differential privacy guarantees across training, inference, and inter-agent data exchange, while preserving sufficient model utility?
- **RQ0:** Does the P2P infrastructure sustain resource sharing without a central coordinator?

## UC4 – End-to-End Adaptive Intelligent Building Community (Full Integration)

### 4.1 Goal

Demonstrate the complete HAAIC Framework operating across a simulated two-unit intelligent building community over a multi-day scenario. This use case integrates all five subsystems simultaneously and exercises all four research questions. It serves as the primary validation scenario for WP6.

### 4.2 Scenario Context

A small research office building with two independently managed units:
- **Unit A** — a shared workspace with 3 occupants (A₁, A₂, A₃) with distinct and occasionally conflicting preferences.
- **Unit B** — a single-occupant study room with Occupant B₁, whose usage patterns are irregular.

The Digital Twin models both units, including HVAC, lighting, CO₂, and occupancy sensors. Both units run dedicated building agents on edge hardware (Raspberry Pi 5). The Kubernetes cluster manages service deployment.

### 4.3 Actors

| Actor | Role |
|---|---|
| Occupants A₁, A₂, A₃ | Workspace users with learned preference profiles |
| Occupant B₁ | Study room user with sparse interaction history |
| Agent A | Manages Unit A (workspace) |
| Agent B | Manages Unit B (study room) |
| HGNN Models (A, B) | Preference inference per unit |
| SLM Dialogue Modules (A, B) | Natural language interaction per unit |
| Digital Twin | Real-time state of both units |
| Kafka Pipeline | Ingests all sensor events from both units |
| K8s Cluster | Hosts containerized services; dynamic provisioning |
| DP Accountant | Tracks privacy budgets for all users |
| P2P Layer | Enables cross-unit resource sharing |
| Dashboard | Monitoring and administrator UI |

### 4.4 Preconditions

- Both units are fully instrumented and connected to the Kafka pipeline.
- All agents and services are deployed on the K8s cluster (Deployment configuration from T6.1).
- Initial preference models are bootstrapped with synthetic profiles (cold-start).
- Privacy budgets initialized: ε_max = 10.0 per user; ε_LDP = 2.0 for cross-unit data.
- Autonomy envelopes configured: temperature ±2 °C of inferred preference; lighting ±100 lux.

### 4.5 Main Flow

The scenario unfolds across **four phases** spanning a simulated working week.

---

#### Phase 1 — Infrastructure Bootstrapping and Warm-Up (Day 1)

1. The K8s deployment scripts provision all containers: Kafka brokers, Digital Twin service, HGNN inference server, SLM instance (per unit), P2P registry, and the monitoring dashboard. *(FR7.1–FR7.3, NFR6.4)*
2. Sensor stubs begin emitting events. The Kafka pipeline ingests events from all zones; the Digital Twin reaches a consistent synchronized state within ≤ 500 ms. *(FR1.1–FR1.4, FR2.4, M-WP3-01)*
3. Agents A and B register with the P2P discovery layer. Each agent performs a self-test: queries the DT, runs a dummy preference inference pass, and logs readiness. *(FR6.5, FR7.1)*
4. The dashboard displays live DT state, agent health, and Kafka consumer lag metrics. *(FR9.1–FR9.4)*

---

#### Phase 2 — Single-Unit Preference Learning (Days 2–3)

5. Occupants A₁–A₃ begin using the workspace. Sensor events (temperature, CO₂, occupancy) are ingested in real time. Agent A infers initial preference vectors for all three users via the HGNN. *(UC1 flow: FR1, FR2, FR3)*
6. Agent A makes autonomous adjustments (temperature, lighting) within its autonomy envelope for each occupant throughout their sessions. All decisions are logged with full context traces. *(FR6.1–FR6.3, NFR7.1)*
7. Occupant B₁ occasionally uses the study room. Agent B detects sparse history (HR@5 < 70%) and issues a P2P request for warm-start embeddings from Agent A (cross-unit transfer, privacy-preserving per UC3 flow). *(FR8.1–FR8.5, NFR3.6–NFR3.8)*
8. DP accountant logs ε expenditure for each query. Budget usage is visible on the dashboard. *(M-PRI-01)*

---

#### Phase 3 — Multi-Occupant Conflict and Dialogue Escalation (Days 3–4)

9. Occupants A₁ and A₃ are simultaneously present in the workspace. Their temperature preferences diverge (A₁: 21 °C vs. A₃: 24 °C). Agent A detects the conflict. *(UC2 flow: FR4.1)*
10. The agent applies the compromise strategy (22.5 °C weighted by session duration). The compromise is within the autonomy envelope → autonomous actuation with both users notified. *(FR4.2, FR6.3)*
11. Next session: A₂ joins. All three occupants have conflicting preferences. The three-way compromise (21.8 °C) is computed. This is within bounds, but Agent A's confidence in A₂'s model is low (ECE > 0.05). *(M-WP4-05)* Agent A proactively initiates an SLM dialogue with A₂: *"I've noticed you've overridden my suggestions twice this week. Could you tell me your preferred temperature for this type of meeting?"* A₂ confirms 22 °C. The preference is persisted. *(FR5.5, FR5.4)*
12. A conflict arises that the agent cannot resolve autonomously (all users' ideal temperatures span > 4 °C). The SLM mediates a three-way dialogue. Consensus is reached in T̄ ≤ 4 turns. *(M-WP5-02)*

---

#### Phase 4 — Resilience, Scalability, and Explainability Validation (Day 5)

13. **Service discovery and dynamic provisioning:** Agent A detects that an energy forecasting microservice is not available in the registry. It requests deployment of the service container on the K8s cluster. The service is registered, deployed, and health-checked within the target window. *(FR7.1–FR7.3, M-WP5-11)*
14. **Fault injection:** The Digital Twin process is killed. Agents A and B enter degraded mode (local sensing continues, cross-unit sync suspended). The DT recovers to a consistent state within ≤ 30 seconds. *(NFR4.1, NFR4.3, M-WP3-04)*
15. **Kafka partition failure:** One Kafka broker is taken offline. The pipeline continues with at-least-once delivery guarantees on remaining brokers. Consumer lag recovers within 60 seconds. *(NFR4.2, M-SCL-02)*
16. **Explainability interaction:** Occupant A₁ asks via the dialogue interface: *"Why did you set the temperature to 22 °C this morning?"* The SLM, grounded in the MCP context (preference model + decision log), provides a traceable explanation citing A₁'s prior acceptance patterns, A₃'s presence, and the compromise strategy applied. *(NFR7.1, NFR7.2, M-USR-04)*
17. **Scale test:** The K8s cluster is scaled to simulate 10 concurrent building agents. Decision cycle latency is monitored at each scale step. *(M-SCL-01)*
18. **Privacy budget exhaustion scenario:** User A₂'s per-session ε budget is deliberately exhausted (via repeated queries). Further external queries for A₂'s data are blocked by the DP accountant. Agent A falls back to the aggregate model for A₂ until the budget resets. *(NFR3.7, M-PRI-01)*

## UC5 – Preference Model Lifecycle: Growth, Pruning, and Abscission

### 5.1 Goal

Validate that the HGNN-based preference model correctly evolves over time: growing new preference nodes as novel contexts are encountered, pruning stale or low-confidence edges, and performing **abscission** — the structured removal of preference signals that are no longer contextually relevant (e.g., summer setpoints during winter, preferences from a past work schedule). The model must remain compact and accurate without requiring full retraining.

This use case isolates the **User Preference Modeling lifecycle (WP4)** subsystem and directly addresses the supervisor-identified gap regarding user model structural evolution.

### 5.2 Actors

| Actor | Role |
|---|---|
| Occupant A | Long-term user with evolving preferences across seasons and routines |
| Building Agent (Zone A) | Triggers model lifecycle operations based on drift signals |
| HGNN Preference Model | Living graph model subject to growth, pruning, and abscission |
| Drift Monitor | Detects significant deviations in preference signal distribution |
| DP Accountant | Tracks privacy budget during incremental retraining |

### 5.3 Preconditions

- Occupant A has at least 20 logged interactions across two distinct contextual periods (e.g., winter and spring).
- The HGNN is structured with typed preference nodes: `(user, context, preference_value, confidence, last_updated)`.
- A staleness threshold is configured: preference nodes not updated in ≥ 30 days are candidates for pruning.
- An abscission policy is defined: nodes with confidence < 0.3 AND context mismatch (e.g., seasonal) are eligible for removal.

### 5.4 Main Flow

1. **Growth — new context encountered:** Occupant A starts using the zone late at night for the first time. No preference node exists for `context: late_night`. The HGNN allocates a new context node with an uninformed prior. The agent defaults to the population average and monitors Occupant A's implicit feedback to grow the node. *(FR3.1, FR3.4)*
2. **Incremental learning:** Over 5 sessions, Occupant A's implicit acceptances (no overrides) populate the late-night preference node with increasing confidence. The node matures from uninformed prior to `{temperature: 20 °C, confidence: 0.78}`. *(FR3.4, M-WP4-01)*
3. **Drift detection:** The Drift Monitor compares Occupant A's spring temperature preferences against the stored winter preferences. A statistically significant shift is detected (p < 0.05, KSWIN). A preference update cycle is triggered. *(FR3.4, M-WP4-03)*
4. **Pruning — low-confidence node removal:** The winter morning preference node for Occupant A has not been reinforced in 35 days and has decayed to confidence 0.22. The agent flags it for pruning. A soft-delete is applied: the node is retained but excluded from inference until it receives new signal. *(FR3.4)*
5. **Abscission — context-invalidated node removal:** The summer-specific preference node (`context: summer, temperature: 26 °C`) is identified as seasonally irrelevant (current season: winter, ≥ 90 days without activation). The abscission policy removes the node from the active graph. The removal is logged with rationale for explainability. *(FR3.4, NFR7.1)*
6. **Model compactness validation:** After a 6-month simulated run, the HGNN graph for Occupant A is evaluated: node count should not grow unboundedly. The ratio of active nodes to total ever-created nodes should remain ≤ 60%. *(M-WP4-07)*
7. **Reactivation:** Occupant A's work schedule changes and the late-night pattern re-emerges after 4 months. The soft-deleted node is reactivated with a decay-adjusted prior rather than starting from scratch. *(FR3.4)*

### 5.5 Alternative Flow – Abscission Conflict

At step 5, if the abscission-candidate node is referenced by an active conflict resolution record (UC2 history), the removal is deferred and the node is retained as a read-only historical anchor. The agent is notified of the deferral.

## UC6 – Ablation Study: Agent Behaviour With vs. Without User Preference Modeling

### 6.1 Goal

Quantify the added value of individual user preference modeling by comparing the HAAIC agent's performance under three conditions: (A) rule-based fixed setpoints (no user modeling), (B) population-average preferences (group modeling, no individual HGNN), and (C) full individual HGNN preference modeling. This use case provides the controlled baseline evidence required to justify the HGNN-based approach as a research contribution.

This use case isolates the **Preference Modeling (WP4)** subsystem in a controlled comparative setting and addresses the supervisor-identified gap regarding management models with/without user modeling.

### 6.2 Actors

| Actor | Role |
|---|---|
| Occupants A₁, A₂ | Two users with distinct, stable, known preferences (ground truth available) |
| Building Agent | Operates under each of the three conditions sequentially |
| Rule-Based Controller (Baseline A) | Applies fixed seasonal setpoints (e.g., 22 °C / 500 lux) |
| Population-Average Model (Baseline B) | Applies preference averages aggregated from historical data |
| HGNN Preference Model (Condition C) | Full individual model as implemented in UC1 |
| Evaluation Module | Records KPIs under each condition for statistical comparison |

### 6.3 Preconditions

- Ground-truth preference profiles for A₁ and A₂ are known (established via UC1 for ≥ 20 sessions).
- The same sensor scenario (fixed context sequence: morning/afternoon/evening, winter week) is replayed identically under each condition to eliminate confounders.
- Override rate and energy consumption are logged per condition.

### 6.4 Main Flow

1. **Condition A — Rule-Based Baseline:** The agent operates with fixed setpoints (temperature: 22 °C, lighting: 500 lux) regardless of occupant identity or context. Override rate, comfort deviation, and energy use are recorded over 5 simulated days. *(FR6.1)*
2. **Condition B — Population-Average:** The agent uses aggregated preference data from a population of 50 synthetic occupants. Setpoints reflect the average (temperature: 21.5 °C ± 1.2 °C, lighting: 480 lux ± 40 lux). Override rate and comfort deviation are recorded. *(FR3.1, FR3.2)*
3. **Condition C — Individual HGNN:** The full HAAIC agent runs with individual HGNN models for A₁ and A₂. Setpoints are personalised per occupant and context. Override rate, HR@5, comfort deviation, and energy use are recorded. *(FR3.1–FR3.5, FR6.1–FR6.3)*
4. **Conflict sub-scenario:** In a multi-occupant session (A₁ and A₂ co-present), the conflict resolution outcome is evaluated under each condition. Condition A has no conflict detection (sets a fixed value). Condition B applies the group average. Condition C applies UC2 conflict resolution. *(FR4.1, FR4.2)*
5. **Statistical comparison:** Mean ± SD of override rate, HR@5, comfort deviation, and energy consumption are compared across conditions using paired tests (Wilcoxon signed-rank). Effect size (Cohen's d) is reported. *(M-WP4-06)*

### 6.6 KPIs Validated

| KPI | Expected Direction |
|---|---|
| M-WP4-01 – HR@5 | C > B > A |
| M-WP4-06 – HGNN vs. Baseline Improvement | Δ ≥ 15% (Condition C vs. best baseline) |
| M-USR-01 – Override Rate | C < B < A |
| M-USR-03 – Comfort Deviation from Stated Preference | C < B < A |
| Energy consumption (secondary) | Monitored; no degradation expected from personalization |

### 6.7 Research Questions Addressed

- **RQ1:** Does individual HGNN preference modeling produce measurably better comfort and lower override rates than rule-based and population-average alternatives?
