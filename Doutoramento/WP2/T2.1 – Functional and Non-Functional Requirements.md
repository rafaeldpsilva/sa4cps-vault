## 1. System Overview

The system under specification is a **Human-Centric Agent-based Adaptive Intelligent Communities Framework** (HAAIC Framework). It operates in intelligent building environments and enables autonomous agents to model user preferences, manage shared resources, and interact with occupants through natural language — all running primarily at the edge.

The system is composed of five interacting subsystems:
1. **Data Ingestion & Digital Twin** (WP3)
2. **User Preference & Context Model** (WP4)
3. **LLM/SLM Interaction Layer** (WP4/WP5)
4. **Agent Control & Autonomy Engine** (WP5)
5. **Monitoring & Frontend** (WP3/WP6)

## 2. Functional Requirements

### FR1 – Data Ingestion

| ID | Requirement |
|----|-------------|
| FR1.1 | The system shall ingest real-time sensor data (temperature, occupancy, lighting, energy, etc.) from building IoT devices via a Kafka-based pipeline. |
| FR1.2 | The system shall support multiple data schemas and heterogeneous sensor types without requiring schema changes at ingestion time. |
| FR1.3 | The system shall timestamp all incoming events with millisecond precision and store them for downstream processing. |
| FR1.4 | The system shall support configurable data topics per zone, device type, and building unit. |

### FR2 – Digital Twin

| ID | Requirement |
|----|-------------|
| FR2.1 | The system shall maintain a real-time Digital Twin of the physical building, reflecting the current state of sensors, devices, and zones. |
| FR2.2 | The Digital Twin shall support simulation of hypothetical states (e.g., "what if occupancy increases in zone A?") for agent planning. |
| FR2.3 | The system shall provide an API to query the current and historical state of any building entity (room, device, zone). |
| FR2.4 | The Digital Twin shall synchronize with the physical environment within a configurable latency threshold. |

### FR3 – User Preference Modeling

| ID | Requirement |
|----|-------------|
| FR3.1 | The system shall represent users, their preferences, context, and building entities in a heterogeneous graph structure. |
| FR3.2 | The system shall train and update a Heterogeneous Graph Neural Network (HGNN) model to infer latent user preferences from sensor observations and interaction history. |
| FR3.3 | The system shall model contextual factors (time of day, occupancy, season, activity) as graph nodes influencing preference inference. |
| FR3.4 | The system shall support incremental model updates as new user interaction data becomes available, without full retraining. |
| FR3.5 | The system shall associate a confidence score with each inferred preference. |
| FR3.6 | The system shall support multi-occupant environments, maintaining separate preference models per user while sharing contextual nodes. |
| FR3.7 | The HGNN training procedure shall use **DP-SGD** (Differentially Private Stochastic Gradient Descent) to bound the influence of any single user's data on the resulting model weights. |
| FR3.8 | The system shall clip per-sample gradients to a configurable maximum L2 norm and add calibrated Gaussian noise during training, with noise scale derived from the target ε and δ parameters. |

### FR4 – Conflict Detection and Resolution

| ID | Requirement |
|----|-------------|
| FR4.1 | The system shall detect conflicts between the preferences of two or more occupants sharing a building zone. |
| FR4.2 | The system shall apply a configurable resolution strategy (e.g., priority-based, negotiation-based, compromise-based) to resolve conflicts autonomously when within the agent's autonomy bounds. |
| FR4.3 | The system shall escalate unresolved conflicts to the affected users via the interaction layer (FR5). |
| FR4.4 | The system shall log all conflict events, resolution strategies applied, and outcomes for post-hoc analysis. |

### FR5 – LLM/SLM Interaction Layer

| ID | Requirement |
|----|-------------|
| FR5.1 | The system shall expose a dialogue interface (text-based) through which occupants can express preferences, ask questions, and receive explanations. |
| FR5.2 | The system shall use a structured Model Context Protocol (MCP) JSON schema to prime LLMs/SLMs with real-time building state and user preference context before each interaction turn. |
| FR5.3 | The system shall support the use of both cloud-based LLMs and locally-deployed SLMs, selectable per deployment configuration. |
| FR5.4 | The system shall extract and persist preference signals inferred from natural language interactions into the user graph model (FR3). |
| FR5.5 | The system shall enable agents to proactively initiate dialogue with users when a decision exceeds the agent's autonomy threshold (FR6.3). |
| FR5.6 | The system shall ensure all LLM/SLM responses are grounded in real-time context, preventing hallucinated references to system capabilities or states. |

### FR6 – Agent Control & Bounded Autonomy

| ID | Requirement |
|----|-------------|
| FR6.1 | Each building unit shall be managed by a dedicated autonomous agent responsible for monitoring, actuation, and user interaction. |
| FR6.2 | Each agent shall make decisions based on the current preference model, Digital Twin state, and contextual data. |
| FR6.3 | Each agent shall operate within a configurable **Bounded Autonomy** envelope; decisions outside this envelope require explicit user confirmation before execution. |
| FR6.4 | Agents shall communicate with each other using a defined inter-agent protocol to coordinate shared resource usage. |
| FR6.5 | Agents shall support dynamic discovery and registration of peer agents within the same community. |

### FR7 – Service Discovery and Dynamic Provisioning

| ID | Requirement |
|----|-------------|
| FR7.1 | Agents shall be able to discover available containerized microservices at runtime via a service registry. |
| FR7.2 | Agents shall be able to request the deployment of new containerized services when a required capability is not available. |
| FR7.3 | The system shall support lifecycle management of deployed services (deploy, monitor, teardown). |

### FR8 – Peer-to-Peer Resource Sharing

| ID | Requirement |
|----|-------------|
| FR8.1 | Agents shall be able to offer and request shared resources (computational capacity, sensor data streams) from peer agents. |
| FR8.2 | Resource sharing shall operate over a P2P protocol that does not require a central broker. |
| FR8.3 | Each agent shall retain the ability to revoke shared resources at any time without disrupting its own operations. |
| FR8.4 | All inter-agent data exchanges shall be scoped to the minimum necessary data (data minimization principle). |
| FR8.5 | Sensor data streams shared between agents via P2P shall be perturbed using LDP mechanisms (e.g., randomized response for categorical data, Laplace/Gaussian mechanism for numerical data) before transmission. |

### FR9 – Monitoring & Frontend

| ID | Requirement |
|----|-------------|
| FR9.1 | The system shall provide a real-time dashboard displaying the current state of the Digital Twin, active agents, and sensor readings. |
| FR9.2 | The dashboard shall display active preference profiles and recent agent decisions per user and zone. |
| FR9.3 | Administrators shall be able to configure autonomy thresholds, service registries, and agent parameters through the dashboard. |
| FR9.4 | The system shall expose a REST API for integration with third-party building management systems. |

## 3. Non-Functional Requirements

### NFR1 – Performance

| ID | Requirement |
|----|-------------|
| NFR1.1 | The data ingestion pipeline shall process incoming sensor events with end-to-end latency under **500 ms** under normal load. |
| NFR1.2 | The agent's decision cycle (sense → infer → act) shall complete within **2 seconds** for routine decisions. |
| NFR1.3 | The LLM/SLM interaction layer shall return a response to user input within **5 seconds** when using a locally-deployed SLM. |
| NFR1.4 | The HGNN preference model inference shall complete within **1 second** per user query. |

### NFR2 – Scalability

| ID | Requirement |
|----|-------------|
| NFR2.1 | The system architecture shall support horizontal scaling to manage at least **50 concurrent building agents** without performance degradation. |
| NFR2.2 | The Kafka-based ingestion pipeline shall scale to handle at least **10,000 events/second** across all topics. |
| NFR2.3 | The graph model shall scale to represent at least **500 users, 10,000 sensor nodes, and 1,000,000 edges** without inference time exceeding NFR1.4. |

### NFR3 – Privacy and Security

| ID | Requirement |
|----|-------------|
| NFR3.1 | All personally identifiable information (PII) and behavioral data shall be processed and stored locally (edge-first), and shall not be transmitted to external services without explicit user consent. |
| NFR3.2 | Inter-agent communication shall be authenticated and encrypted (TLS 1.3 minimum). |
| NFR3.3 | Each user's preference model shall be isolated and inaccessible to other agents or users without explicit sharing consent. |
| NFR3.4 | The system shall comply with GDPR requirements, including the right to access and delete personal data. |
| NFR3.5 | Audit logs of all agent decisions and data accesses shall be maintained and tamper-evident. |
| NFR3.6 | The system shall enforce **differential privacy** guarantees (ε-DP) on all aggregated user preference data shared across agents or exported externally, with a configurable privacy budget ε. |
| NFR3.7 | The privacy budget (ε) shall be tracked per user and per data release; once exhausted, further queries on that user's data shall be blocked until the budget resets. Budget composition shall use Rényi DP / zCDP to account for cumulative privacy loss across training rounds and queries. |
| NFR3.8 | The system shall apply **Local Differential Privacy (LDP)** at the sensor/edge level before raw behavioral data leaves the building unit, ensuring the aggregator never receives unperturbed individual data. |

### NFR4 – Reliability and Fault Tolerance

| ID | Requirement |
|----|-------------|
| NFR4.1 | The system shall maintain core agent functionality (local sensing, actuation, preference inference) even when network connectivity to peer agents or cloud services is unavailable. |
| NFR4.2 | The Kafka pipeline shall guarantee at-least-once delivery of sensor events. |
| NFR4.3 | The Digital Twin shall recover to a consistent state within **30 seconds** of a component failure. |
| NFR4.4 | Agent state shall be persisted such that a restart recovers the agent to its last known consistent state. |

### NFR5 – Edge Compatibility

| ID | Requirement |
|----|-------------|
| NFR5.1 | The agent core, preference inference module, and SLM shall be deployable on devices with **≥4 GB RAM** and **≥4-core ARM/x86** processors (e.g., Raspberry Pi 5, NVIDIA Jetson). |
| NFR5.2 | The SLM selected for local deployment shall have a parameter count compatible with inference on the target edge hardware without GPU acceleration. |
| NFR5.3 | The system shall minimize unnecessary background network usage to preserve bandwidth on constrained links. |

### NFR6 – Maintainability and Extensibility

| ID | Requirement |
|----|-------------|
| NFR6.1 | All system components shall be implemented as independently deployable microservices with well-defined REST or message-based interfaces. |
| NFR6.2 | The HGNN graph schema shall be versioned to allow schema evolution without full retraining. |
| NFR6.3 | The MCP JSON schema shall be versioned and documented such that new LLM/SLM models can be integrated by updating the schema without code changes. |
| NFR6.4 | All components shall expose health-check endpoints compatible with Kubernetes liveness and readiness probes. |

### NFR7 – Explainability

| ID | Requirement |
|----|-------------|
| NFR7.1 | The agent shall be able to provide a natural language explanation of any decision it made, traceable to the preference model and contextual inputs. |
| NFR7.2 | The HGNN model shall expose attention weights or equivalent attribution scores to support explanation generation. |

### NFR8 – Interoperability

| ID | Requirement |
|----|-------------|
| NFR8.1 | The system shall expose a standard REST API for external integration (e.g., existing BMS, Home Assistant). |
| NFR8.2 | Sensor data ingestion shall support standard IoT protocols (MQTT, HTTP/REST) as input adapters to the Kafka pipeline. |
| NFR8.3 | The agent's service discovery mechanism shall be compatible with standard container orchestration (Kubernetes, Docker Swarm). |

## 4. Constraints

| ID | Constraint |
|----|------------|
| C1 | The system must operate primarily at the edge; cloud dependency must be optional and configurable. |
| C2 | All software components must be open-source or developed within the project. No proprietary lock-in for core functionality. |
| C3 | The system must be demonstrable within the Digital Twin environment defined in WP3 prior to real-pilot deployment. |
| C4 | The system shall be containerized (Docker) and deployable via Kubernetes as defined in WP6. |
| C5 | The privacy budget parameters (ε, δ) shall be defined per deployment and documented in the Data Management Plan (T2.5). Typical targets: ε ∈ [1, 10] for utility-preserving settings; ε < 1 for high-sensitivity contexts. |

---

## 5. Assumptions

- Building sensor infrastructure (IoT devices, network) is pre-existing or provided by the pilot environment.
- Users interact with the system voluntarily and provide explicit consent for preference data collection.
- At least one edge device per building unit is available for agent deployment.
- The Digital Twin simulation environment (WP3) is sufficient as a validation testbed before real-world pilots.
